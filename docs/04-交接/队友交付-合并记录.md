## 二、✅ 采纳（9 组 · 已录入本项目文档）

### 1. 文档治理与优先级声明（他的 §1）

**采纳原文口径**：

- 本文件明确裁定的事项，覆盖**此前与之冲突的建议**；
- 未修改的玩法继续采用**最终原始规则文件**；
- **"工程建议"和"待导入数据"不能自动升级为已确认玩法**；
- **历史举例、测试条件和估算不得自动成为正式参数**；
- 配套 JSON 是**完整市场模块配置，不是整套游戏的完整配置**——程序不得因市场配置齐全，就认定生产、建设、服务和幸福度也已齐全。

> **为什么采纳**：与我们《README §八 文档权威顺序》和基线"不得为填满配置而编造数据"完全同向。
> ⚠️ **一处收口**：他的"本文件覆盖此前冲突建议"**不能覆盖**①用户最新口头裁定、②《规则基线》。本次四个冲突点即按此收口。

### 2. AI 秘书（他的 §2.1 / §2.2 / §2.3）— 用户已确认一致

**定位**：玩家无需先理解全部规则才能游玩。AI 秘书负责回答规则问题、查询当前局面、给出生产/采购/建设/服务规划、比较方案、解释成本收益限制与风险；**玩家可以接受或拒绝**。

**执行边界（采纳为硬约束，写进 `ai/` 层）**：

| 角色 | 能做什么 |
|---|---|
| **AI 秘书** | 只解释与规划。**未经玩家确认**：不提交正式 Plan、不改变玩家状态、不购买、不建设、不结束季度 |
| **规则引擎** | 合法性校验、精确计算、状态变更、季度结算 |

- AI **不得自行创造**配方、价格、权重或例外规则；
- 精确金额、投入数量、效率和收益预测**必须来自确定性计算器**；
- **缺失规则或数据必须明确报出**，不得以语言推测代替正式计算。

**建议接口（采纳为服务层命名建议）**：

```
get_rules       查询规则和版本
get_state       查询玩家状态
validate_plan   校验方案，不改变状态
simulate_plan   试算方案，不改变状态
submit_plan     玩家确认后正式提交
```

- 试算结果应**包含规则版本及状态版本**；正式执行前**重新校验**，防止执行过期方案。

> **与我们既有架构的对应**：`simulate_plan` = 我们已有的 `preview()`（[`AI自主演算-架构影响.md`](../03-架构/AI自主演算-架构影响.md) §6），`validate_plan` = `tool_validate`，`submit_plan` = 服务端 `submit`。**命名采纳，架构不变**——仍是"`preview` 与 `advance` 共用实现、AI 永远调不到 `advance`"。

### 3. 地块建模与作废错误假设（他的 §3）

- **地块五层区分采纳**：`land_type`（类别）/ `plot`（实例）/ `level`（等级）/ `recipe`（配方）/ `good`（商品）。与基线 §2.2、§0 一致。
- **作废"3×4 地图 / 共 12 块地 / 一个商品对应一块地"** → 采纳。本项目**早已作废**（地图已定 10×10）。
- **"商品数量不等于地块数量""采购上限不等于土地数量或生产规模"** → 采纳。
- **"本文件不新增第五类地块"** → 采纳，且**与原研究地块不矛盾**：他 §3.1 列的是四类"主要类别"，§3.3 明确"**研究功能按原始研究及升级路径实现**"。本项目研究地块是原始规则既有，非第五类新增。

### 4. 季末全部出售（他的 §5）— ★ 实质性补充

**采纳，且强化了我们的基线**：

- 季末出售**全部尚未消耗**的中央市场可交易商品库存；
- **不存在"合法工程预留"**；仅计划以后用于工程的材料，季末**也必须出售**；
- **出售量[g] = 清仓时普通库存[g]**；`销售收入 = 出售量 × 参考价`；**清仓后普通库存 = 0**；
- **执行顺序约束**：本季生产、工程材料投入、生活消费扣减，**必须在最终清仓出售前完成**；不得先把生活物资卖出、再凭空完成本季消费。

**以下对象不出售（采纳）**：已消耗原料、已生活消费物资、**已投入工程并从普通库存扣除的材料**、不可交易的本地服务 `J`、已建成地块与设施等非商品资产。

**示例（采纳，可直接当测试用例）**：

| 情形 | 结果 |
|---|---|
| 库存 5 单位 H-G，准备下季升级 | **本季末全部出售** |
| 5 单位 H-G 已投入**已启动工程** | **不出售**，也不再出现在普通库存 |
| 多买 10 单位 A，本季未消耗 | **本季末全部出售** |
| 未使用的服务能力 | 不作为中央商品出售，不转为 `J` 库存 |

> **为什么这是补充**：基线 §6 第 9 步只写了"**不保留普通待售库存**"，**没说这些货去哪了**。他补上了关键一环——**是"清仓变现"，不是"蒸发"**。这直接影响期末现金。已同步进基线 §6、§11。

### 5. 工程材料分账（他的 §6）

**采纳**：工程启动并正式接受材料时——**普通库存减少；工程记录已投入材料**。

- ❌ 材料仍保留在普通库存，同时又认定工程已取得材料；

- 错误信息至少含：**错误类型 / 涉及商品或地块 / 申请值 / 可用值 / 差额**。

## 三、❌ 驳回（3 组 · 与用户 2026-10-16 裁定相反）

### 1. 市场模型：固定价 → **驳回，用动态供需曲线**

**他的主张**（§4）：按参考价买入、按同一参考价卖出、无买卖价差、无额外交易手续费；**首版禁用动态定价**；不依赖 `Q0`、`Es`、`Ed`；不得把采购上限当成动态市场 `Q0`。

**用户裁定**：**用动态供需曲线**（基线现方案）。

**本项目保留的**（基线 §4.1）：

```
s = Es × Q0 / P0        d = |Ed| × Q0 / P0
P_t = P0 + (B_t − X_t) / (s + d)
P_min = 0.1 × P0
```

**买入按【上季结算价】、卖出按【本季价】——但两步都在【结算时】发生**（✅ 2026-10-16 定案）：
玩家阶段（期初）**只提交 Plan，不扣钱、不锁价、不动账户**；物资款（按上季价）+ 工资 + 经营费在结算时**一笔扣清**。
`B_t` = 生产原料 + 建设物资 + 居民口粮（**三段全计入**），所以**买入量会把本季 `P_t` 顶高**。
价格触底时**按可实现需求量分配成交，不保证全量收购**，未售商品清理、不产生收入。

**他的内容中，仍然成立的部分**：

- `buy_price_multiplier = 1.0` / `sell_price_multiplier = 1.0` / `transaction_fee_rate = 0.0` → 与基线一致（动态曲线下 `P_t` 是唯一成交价，无价差；基线无手续费）。**可作为动态模式的默认乘数保留**。
- `sell_all_tradable_inventory_at_quarter_end = true` → ✅ 采纳（见 §二-4）。
- `construction_inventory_reservation_allowed = false` → ✅ 采纳（见 §二-5）。
- `purchase_phase = quarter_start` / `sale_phase = quarter_end_after_consumption` → ✅ 与基线 §6 时序一致（**2026-10-16 补注**：`purchase_phase` 仅指采购的**申报**发生在玩家阶段，**付款与记账都在结算时**——玩家阶段不扣钱，见 §三-1 与基线 §4.1 / §6）。

**明确驳回的**：

| 他的写法 | 驳回理由 |
|---|---|
| `dynamic_pricing.enabled = false` | 用户裁定启用动态曲线 |
| "不执行动态价格触底限售" | 与基线 `P_min` 机制直接冲突 |
| `central_purchase_from_player_unlimited = true`（中央收购无上限） | 基线是"曲线 + `P_min` + 按可实现需求分配"，**不保证全量收购** |
| "不执行旧版 30、15、10 等固定收购限制" | ✅ 与 2026-10-16 裁定**方向一致**（都是取消）：本项目是**彻底停用**，不是"暂予保留"。见 §四-2 |

### 2. 人口：`N = L` → **驳回，保持 `N = L×2`**（✅ 2026-10-16 取消取整）

**他的主张**（§8）：`N = L = Σ(d × u)`，`d` 为劳动系数、`u` 为开工量；并特别强调**人口"不乘 2"、不乘效率 E**、可为小数人口当量、停工不产生用工。

**用户裁定**：**保持 `N = L×2`**（`r = 2`）。

> **本项目口径**（基线 §3.3.1）：`L = Σ(d×u)` 岗位数 → `N = L × 2`，`r = 2` 为"总人口 / 劳动力比例"。

### 3. 邻接：保留"关联度/等级权重" → **驳回，保留八邻格＋关联表＋5%/40%**

**他的主张**（§7）：保留原规则的**关联度和等级权重**计算方式；撤销"仅同类相邻""删除关联度""删除等级权重""用统一简化表替换原邻接表"；并**禁止默认**：所有关联度=1、所有等级权重=1、只算同类、自动对称化、**自动采用四邻接或八邻接**；"不能因为原表缺失，就默认为……"。

**用户裁定**：**保留我们已定案的八邻格＋关联表＋5%/40%**。

**本项目口径**（基线 §3.1 / §3.2 / §3.6）：

```
E_邻接 = 1 + min(0.05 × N_关联, 0.40)
N_关联 = 八邻格中【类型落在关联表上】的那些
```

| 地块类型 | 关联地块类型 | 每邻居 | 上限 |
|---|---|---|---:|
| 农业 | 农业、资源 | +5% | +40% |
