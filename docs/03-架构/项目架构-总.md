## 一、这是个什么程序

**一句话**：**一个确定性的季度结算引擎 + 一层只转发的服务 + 一个只显示的界面。**

```
玩家点操作  →  打包成 Plan  →  服务端收齐  →  引擎一次算完  →  月报  →  下一季
```

**它不是**：实时游戏、有物理的游戏、需要渲染引擎的游戏、有并发竞争的游戏（**同一局串行处理，见 §3.5**）。

| 看起来像 | 实际是 |
|---|---|
| 模拟经营游戏 | 确定性状态机 |
| 需要游戏引擎 | **一行都不需要** |
| 复杂 AI | AI 只写文案 |
| 实时多人 | **回合制 + 屏障结算** |

## 三、回合循环与状态机

### 3.1 唯一的循环

```
① 行动阶段（唯一的"共同"阶段，每人只能提交一次）
        ↓  所有人点"结束季度"
② 季度结算（服务端一次性算完）
        ↓
③ 月报
        ↓
④ 下一季行动阶段（回到 ①）
```

### 3.2 三状态机

```python
class Phase(str, Enum):
    COLLECTING = "collecting"    # 行动阶段：等玩家提交
    RESOLVING  = "resolving"     # 结算中（瞬时）
    REPORT     = "report"        # 月报已出
```

```
COLLECTING  →  RESOLVING  →  REPORT  →  COLLECTING
```

### 3.3 单人 = 多人的特例

```
多人：p1提交, p2提交, p3提交 → 全齐 → 结算
单人：p1提交 → 全齐（len==1）→ 立即结算
```

**单人没有任何等待逻辑。** `len(plans) == len(players)` 在单人时提交即成立。

> 这就是"收齐 plans 再结算"这条红线为什么是对的——**它是多人的默认行为，单人时自动退化**。

### 3.4 "只能提交一次"消掉的一整类问题

| 原本要处理的 | 现在不需要 | 为什么 |
|---|---|---|
| 请求队列 | ❌ | 没有并发请求（**但见 §3.5：仍要一把串行锁**） |
| 冲突合并 | ❌ | 没人能改 |
| 乐观锁 | ❌ | 写入即锁定 |
| "以最后一次为准" | ❌ | 只有一次 |
| 重复提交幂等 | ❌ | 第二次直接拒绝 |

**`plans` 是"只增不改"的字典**：

```python
plans[player_id] = plan     # 一次写入，永不修改
```

### 3.5 并发：同一局一把锁，全部串行（✅ 2026-10-16 定案）

> **依据**：[规则基线 §1.3.1](../01-规范/规则基线.md)。

**服务层对同一局只允许一个请求在跑，全部串行。** 不是"乐观锁"，不是"版本号"，就是**一把锁**。

```
同一 game_id 上：一个请求进 → 拿锁 → 算完 → 释放 → 下一个才能进
```

| 为什么需要 | 说明 |
|---|---|
| `advance()` 会**整体改写状态** | 两个请求同时跑 = 状态被交叉覆盖，账必错 |
| 结算必须"**一次算完**" | 中途被打断会留下半个季度，比崩溃更难查 |
| 不用复杂方案 | 第一阶段就是一把锁，不要乐观锁 / 版本号 / 事件溯源 |

**落地要点（四条）**：

| # | 规则 |
|---|---|
| 1 | **锁的粒度是"每局一把"**（`game_id` → `Lock`），不是全局一把——不同局互不阻塞 |
| 2 | **提交计划也走串行**：`plans` 只增不改，配合锁天然满足"一个玩家只能提交一次" |
| 3 | **单人期 `len(plans)==1` 立即结算**，锁内完成，不留等待态 |
| 4 | **锁在 `try/finally` 里释放**，异常也必须放锁，否则整局卡死 |

> ⚠️ **锁在服务层，不在引擎里**。`engine/` 是纯函数，**不知道锁的存在**；
> 锁只活在 `server/session.py`。这样引擎仍能脱离 Web 单独跑测试——与 §二 的分层红线一致。
>
> ⚠️ **这不是 §八 说的那类"防并发写库"**（那一类在本模型下不成立）。
> 这里挡的是**同一个 HTTP 端点被重复点两次 / 重放**，属于最朴素的一类并发。

> ⚠️ **与 §3.4 的关系**："只能提交一次"消掉的是**业务层**的冲突（没人能改已提交的计划）；
> 本节这把锁消掉的是**传输层**的冲突（同一个请求被发了两遍）。**两者都要，互不替代。**

## 四、五条写法红线

**功能上只做单人（第一期），代码结构按多人写（未来）。**

| # | 红线 | ✅ | ❌ |
|---|---|---|---|
| 1 | **玩家身份永远用 `player_id` 索引** | `state["players"]["p1"]["cash"]` | `state["cash"]` |
| 2 | **共享 / 私有分层** | 共享：市场价、曲线、政策、时钟 | 现金和价格塞同一个 dict |
| 3 | **收齐所有计划再结算** | `advance(plans: Dict[PlayerId, Plan])` | `advance(state, plan)` |
| 4 | **分配规则做成可替换策略** | 注入 `allocator` | 写死"先到先得" |
| 5 | **服务层只转发** | `POST /state?player=p1` | 在路由里算价格 |

**第 1 条最贵**——把玩家状态摊在顶层，以后改多人几乎等于重写。

**单→多扩展的全部代价 = 三处**：
```python
players: dict[str, PlayerState]     # ① players 字典
def f(state, player_id, ...)        # ② player_id 参数
def advance(state, plans: dict)     # ③ plans 字典
```

> **这五条和业界成熟模式是对上的**：
> `advance(plans)` = 分阶段屏障 ｜ `allocator` = 分配策略 ｜ `player_id` = 状态分区
> 服务层只转发 = 服务端权威 ｜ `Plan` = Command Pattern

## 六、引擎：季度流水线

**这是程序的"心脏"，一个纯函数。**

```python
def advance(state: GameState, plans: dict[str, Plan]) -> GameState:
    # —— 第一期唯一的多余代码 ——
    assert len(plans) == 1        # 单人；多人时删掉这行即可

    # 1. 应用计划
    for pid, plan in plans.items():
        apply_plan(state, pid, plan)

    # 2. 效率（服务走独立分支）
    for pid, plan in plans.items():
        for plot in state.players[pid].plots.values():
            plot.efficiency = compute_efficiency(state, pid, plot)

    # 3. 人口与粮食需求
    for pid in plans:
        update_population(state, pid)      # L → N → ḡ → m → F_基准/F_优秀

    # 4. 生产                                        ★ 2026-10-16：原第 4 步"期初采购"删除
    for pid, plan in plans.items():
        run_production(state, pid, plan)   # 产量 = e·u·E；同时算清本季的商品投入需求

    # 4.5 买入汇总与求价                             ★ 2026-10-16 新增
    #     B_t = 生产原料 + 建设物资 + 居民口粮（三段全部计入）
    #     P_t = P0 + (B_t − X_t)/(s+d)      ← 买入量顶高本季价
    for pid, plan in plans.items():
        aggregate_purchases(state, pid, plan)   # 只汇总数量，不扣钱、不锁价
    settle_price(state)                         # 求出本季 P_t

    # 5. 一次性扣款                                   ★ 2026-10-16 新增，唯一的扣款点
    for pid, plan in plans.items():
        settle_payment(state, pid)     # 物资款（按【上季价】）+ 工资 + 经营费，一笔扣清

    # 6. 建设推进
    for pid in plans:
        advance_construction(state, pid)

    # 7. 市场结算（共享资源，一起算）
    settle_market(state, allocate_proportional)   # 产出按本季 P_t 卖出

    # 8. 粮食结算 → H    ★ 必须在 7 之后
    for pid in plans:
        settle_food(state, pid)

    # 9. 税收 / GDP
    for pid in plans:
        settle_taxes(state, pid)

    # 10. 结转
    state.world.quarter += 1
    return state
```

> ⚠️ **玩家阶段（行动阶段）一分钱都不扣**（✅ 2026-10-16）：玩家在 `COLLECTING` 里**只提交 `Plan`**——
> 只是**写意愿**，不扣钱、不锁价、不动账户。所有现金变动**只在第 5 步发生**，且**一笔扣清**。
> 所以"期初采购"这个说法作废：买是**结算时按上季价记账买入**，落点在**价格**上，不在**时点**上。
> 见 [规则基线 §4.1](../01-规范/规则基线.md) 交割时序 与 §6 季度执行顺序。

> ⚠️ **连锁关系（容易漏）**：第 4.5 步汇总出的 `B_t` **要加进第 7 步的需求侧**——
> 也就是**买货这个动作本身会把本季价格顶上去**，代价在季末体现。
> 买入锁在**上季价**、卖出随**本季价**，两者价差就是交割成本。

> ⚠️ **首季没有"上季价"** → 用参考价 `P0` 兜底（M1 初始条件即如此）。

### 六条顺序铁律（**真正的风险点**）

**这个项目的难点不是算法，是求值顺序。** 写错任何一条，数字就对不上且极难查。

| # | 铁律 | 为什么 |
|---|---|---|
| 1 | **幸福度用上一季的 H** | 否则循环依赖，算不出来 |
| 2 | **粮食在结算时扣**（第 8 步） | 期初是玩家支配资金，买不买粮是他的选择 |
| 3 | **买入按上季价记账、卖出按本季价，但扣款全部集中在结算时（第 5 步）一笔扣清** | 时序。玩家阶段**只写意愿、不扣钱、不锁价、不动账户**；"期初按上期价买"是口语说法，落点在**价格**不在**时点** |
| 3b | **买入量进本季需求侧，把本季价格顶上去**（第 4.5 步的 `B_t` → 第 7 步的 `P_t`） | 否则"买货推高价格"这条连锁丢失，囤货无代价 |
| 4 | **劳动不乘 E**（`劳动 = d·u`） | 效率高只是同样的人干更多批次 |
| 5 | **本季产出不能倒填本季已开始的生产** | 铁律 |
| 6 | **粮食结算必须在市场结算之后** | 否则卖不掉的东西不能拿来吃 |

> ⚠️ **第 3 条本轮改口径（2026-10-16）**：旧写法是"**期初**按上期价买、**季末**按本期价卖"，读起来像**两次动账户**。
> 新写法把**时点**与**价格**拆开：**价格**仍是"买入用上季价、卖出用本季价"（不变），
> 但**扣款只发生一次**——第 5 步"一次性扣款"（物资款 + 工资 + 经营费），**从公用账户一笔扣清**。
> 见 [规则基线 §6](../01-规范/规则基线.md) 与 §4.1 交割时序。

## 七、服务端

```python
class GameSession:
    def __init__(self, state, player_ids):
        self.state = state
        self.player_ids = player_ids
        self.plans: dict[str, Plan] = {}      # ← 只增不改
        self.phase = Phase.COLLECTING
        self.lock = threading.Lock()          # ★ 每局一把锁（§3.5）

    def submit(self, player_id: str, plan: Plan):
        with self.lock:                       # ★ 同一局全部串行
            if self.phase != Phase.COLLECTING:
                raise Conflict("不在行动阶段")
            if player_id in self.plans:
                raise Conflict("已提交，不能修改")    # ← 只能提交一次
            validate_plan(self.state, player_id, plan)   # 服务端校验
            self.plans[player_id] = plan

    def end_quarter(self, player_id: str):
        with self.lock:                       # ★ 收齐判定也在锁内
            if len(self.plans) == len(self.player_ids):
                self._resolve_unlocked()

    def _resolve_unlocked(self):
        # ⚠️ 调用方必须已持锁
        self.phase = Phase.RESOLVING
        engine.advance(self.state, self.plans)   # ★ 一次性算完
        save_snapshot(self.state)                 # ★ 立刻存档
        self.plans.clear()
        self.phase = Phase.REPORT
```

> ⚠️ **锁的写法铁律（2026-10-16）**：**一律用 `with self.lock:`**（等价于 `try/finally` 释放锁）。
> 若手写 `acquire()`，**必须**配 `try: ... finally: self.lock.release()`——
> **异常也要放锁**，否则一次报错就把整局永久卡死。
>
> ⚠️ **锁内只做状态改动，不做 IO / 不调 LLM**。`save_snapshot` 之外的耗时操作移出锁外，否则串行会变成卡顿。

**接口只有几个**：

```
GET  /state?player=p1        → 拿当前状态（已算好的数字）
POST /submit                 → 提交计划
POST /end_quarter            → 结束季度
GET  /report?player=p1       → 拿月报
```

> **铁律**：路由里**不算价格、不做插值、不改状态**。全部交给 `engine/`。

**引擎只依赖 `Storage` 接口，不知道背后是文件还是数据库。**

> ⚠️ **修正上一轮的建议**：我之前说"多人存储要防并发覆盖"——**在你这个模型下不成立**。
> 因为**不存在两个请求同时写同一局**：行动阶段是收集，结算是单点触发。
> 所以 `revision` / `command_log` **从"必需"降为"可选"**（字段可留，但不是为并发）。
>
> ⚠️ **2026-10-16 补充边界**：上面这条说的是**存储层**不需要防并发（不是"防并发写库"那类问题）。
> 但**服务层仍要一把串行锁**——挡的是同一个 HTTP 端点被重复点两次 / 重放。见 §3.5 与 [规则基线 §1.3.1](../01-规范/规则基线.md)。
> **两件事层次不同，别用本节去否掉 §3.5。**

**存档时机**：结算完**立刻全量快照**（唯一的持久化时机，在锁内完成）。

## 十二、四条关键纪律

| # | 纪律 | 原因 |
|---|---|---|
| 1 | **`advance()` 必须是纯函数** | 结算一次算完，**出错没有中间状态可回退** |

| 3 | **`plans` 只增不改** | 别写成允许覆盖 |

## 十四、一句话总结

> **架构 = 一个纯函数引擎（十步流水线）+ 一个三状态服务（每局一把锁）+ 一个只显示的前端。**
>
> - **规则自己写**（世上没有规则一致的开源实现）
> - **架构抄成熟模式**（Command / 纯函数 / 屏障结算 / 服务端权威）
> - **守五条红线**（`player_id` / 分层 / `advance(plans)` / `allocator` / 只转发）
> - **真正的风险是求值顺序**，不是算法难度
> - **钱只在结算时动一次**（第 5 步一次性扣款），**玩家阶段不扣钱**
>
> **项目价值在规则，代码只是规则的翻译。**
