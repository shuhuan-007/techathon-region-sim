# 游戏架构参考：值得借鉴的模式

> 上一版回答偏"要不要用库"。这一版回答**架构本身**：
> 这类游戏（回合制 / 状态机 / 未来多人）**业界是怎么搭的**，哪些模式值得抄。
>
> 全部结论有出处，末尾附参考清单。

---

## 一、先给你的游戏定位

**你的游戏在架构史上属于哪一类？**

| 维度 | 你的游戏 | 对应架构流派 |
|---|---|---|
| 时间模型 | **回合制**（一季一次推进） | Turn-based / Lockstep |
| 状态模型 | **确定性状态机**（同样输入→同样输出） | Deterministic Simulation |
| 输入模型 | **玩家提交"命令"**（开工/购买/建设） | **Command Pattern** |
| 并发模型 | 现在单人，未来多人**同时提交** | **Simultaneous Turns** |
| 持久化 | 一个存档文件，未来多局多玩家 | **Snapshot + Event Log** |

> **关键洞察**：你这游戏和 **[boardgame.io](https://github.com/boardgameio/boardgame.io)**（12k star，MIT）
> 是**同一个架构族**——"回合制 + 命令 + 服务端权威 + 状态同步"。
> 虽然它是 JS，**但它的架构思想可以直接搬**。下面很多结论来自它。

## 二、模式一：Command Pattern（最该抄的一个）

### 2.1 是什么

出处：[Game Programming Patterns · Command](https://gameprogrammingpatterns.com/command.html)（业界公认参考书）

> **A command is a reified method call.** —— 命令就是"被变成对象的函数调用"。

**别让玩家操作直接改状态，而是让它生成一个"命令对象"：**

```python
# ❌ 不要这样
def on_click_build(plot_id):
    state.players["p1"].cash -= 800      # 直接改状态
    state.players["p1"].plots[plot_id].state = "building"

# ✅ 这样
@dataclass
class BuildCommand:
    player_id: str
    plot_id: str
    build_type: str
```

### 2.2 为什么你的项目**特别**需要它

你现在的 `Plan` 其实**已经是命令集合**了，只是没这么叫：

```python
@dataclass
class Plan:
    player_id: str
    plot_plans: dict[str, PlotPlan]     # ← 一批命令
    purchases: dict[str, float]         # ← 一批命令
    builds: list[BuildOrder]            # ← 一批命令
    contracts: list[ContractAction]     # ← 一批命令
```

**把这个思路贯彻到底，你会白拿四个能力**：

| 能力 | 怎么来的 | 对你的价值 |
|---|---|---|
| **存档** | 存命令序列 | 存档变小；还能"回放"整局 |
| **回放 / 观战** | 重放命令 | 黑客松演示神器 |
| **AI 托管** | AI 生成命令，走同一条路 | "自动演示模式" |
| **多人** | 命令可序列化 → 可网络传输 | **正好是你的需求** |

> 书里原话：**"If we take those commands and make them serializable, we can send the stream of them over the network."**
> —— 把命令变成可序列化的，就能在网络上传输。**这就是多人的基础。**

### 2.3 具体怎么做

```python
# 命令是纯数据，可 JSON 序列化
@dataclass
class Command:
    player_id: str
    kind: str                  # "build" | "set_run_ratio" | "purchase" | ...
    payload: dict

# 命令 → 状态变换（纯函数）
def apply_command(state: GameState, cmd: Command) -> GameState:
    handler = HANDLERS[cmd.kind]
    return handler(state, cmd)

HANDLERS = {
    "build":         cmd_build,
    "set_run_ratio": cmd_set_run_ratio,
    "purchase":      cmd_purchase,
}
```

**纪律**：**所有状态修改都必须经过命令。** 书里说这句话时用了 "It takes discipline"——这是唯一的成本。

## 三、模式二：纯函数状态更新（Immutability）

### 3.1 boardgame.io 的做法

它强制要求所有 move 是**纯函数**：

> "you cannot depend on any **external state**, nor can you have any **side-effects**"
> —— 不能依赖外部状态，也不能有副作用。

```js
function move({ G }) {
  return { ...G, hand: G.hand + 1 };   // 返回新状态，不改原状态
}
```

**它给的收益（原文）**：

> "you can ensure **repeatability** (moves can be replayed over a particular state value multiple times in different places)
> and you can do **cheap comparisons** to check if something changed."

| 收益 | 对你的价值 |
|---|---|
| **可重复性** | 同状态+同命令 → 同结果，**测试极好写** |
| **便宜的比较** | `new_state != old_state` 立刻知道有没有变化 |
| **可回放** | 能回到任意历史状态 |

### 3.2 你要不要做

**建议：部分做。**

| 做 | 不做 |
|---|---|
| ✅ `advance()` 尽量**不读全局变量** | ❌ 不必强求 `state` 完全不可变 |
| ✅ 状态从参数进、从返回值出 | ❌ 不必引入 `immutables` 库 |
| ✅ 不依赖当前时间、随机数 | |

**原因**：Python 里做到完全不可变很啰嗦（要 `deepcopy` 或 frozen dataclass）。
**你的收益主要来自"确定性"，而这个用纪律就能保证，不用库。**

> ⚠️ **一条硬要求**：**不要用 `random`，不要用 `datetime.now()`。**
> 用了就破坏确定性，M1 数字会对不上。

## 四、模式三：服务端权威（Server Authoritative）

### 4.1 概念

**客户端只发意图，服务端算真相。**

```
玩家点"建农业"  →  客户端发命令  →  服务端校验+执行  →  广播新状态
                                       ↑
                                  ★ 真相在这里
```

### 4.2 为什么你**必须**这么做

你的铁律已经写死了：

> **程序决定事实，AI 只负责解释**

再加一条前端铁律：

> **前端只显示、零计算**

**这两条合起来就是"服务端权威"** —— 你已经决定做了，只是没起这个名字。

### 4.3 落到代码

```python
# server/app.py
@app.post("/advance")
def post_advance(player: str = "p1", plan: Plan = Body(...)):
    # 1. 校验（服务端做，不信客户端）
    if not validate_plan(state, player, plan):
        raise HTTPException(400, "非法操作")
    # 2. 执行（真相在服务端）
    engine.advance(state, {player: plan})
    # 3. 返回（客户端只显示）
    return serialize(state, player)
```

> **这一条现在单人也要守。** 因为以后多人时，**客户端传来的东西永远不可信**。

## 五、模式四：状态持久化（你问的第 1 点）

### 5.1 三种方案

| 方案 | 存什么 | 优点 | 缺点 |
|---|---|---|---|
| **Snapshot**（快照） | 当前完整状态 | 简单、读得快 | 大；无历史 |
| **Event Log**（事件日志） | 命令序列 | 小；可回放/审计 | 读要重放 |
| **混合**（推荐） | 快照 + 之后的命令 | 兼顾 | 稍复杂 |

### 5.2 对你的建议

**第一期：纯 Snapshot。** 但**结构上为 Event Log 留位**。

```json
{
  "schema_version": 1,
  "game_id": "g_20261016_001",
  "saved_at_quarter": 7,
  "world": { "...": "共享状态" },
  "players": { "p1": { "...": "私有状态" } },
  "command_log": [
    { "quarter": 1, "player_id": "p1", "kind": "build", "payload": {...} },
    { "quarter": 1, "player_id": "p1", "kind": "set_run_ratio", "payload": {...} }
  ]
}
```

**为什么现在就加 `command_log`**：

| 理由 | 说明 |
|---|---|
| **成本极低** | 就是 append 一个 list |
| **调试神器** | bug 复现时，重放日志即可 |
| **未来多人必需** | 服务器要知道"谁在什么时候做了什么" |
| **可回放** | 黑客松演示可以"播放整局" |

> ⚠️ **关键设计**：**命令日志要能重放出完全相同的结果。**
> 这就回到"确定性"——**只要不用随机数和系统时间，重放必然一致。**

### 5.3 多人的存储适配（你问的重点）

**现在就要把"存储"和"状态"分开：**

```python
# ❌ 不要：状态直接读写文件
def advance(state, plans):
    ...
    json.dump(state, open("save.json", "w"))

# ✅ 这样：存储层可替换
class Storage(Protocol):
    def load(self, game_id: str) -> GameState: ...
    def save(self, game_id: str, state: GameState) -> None: ...
    def append_command(self, game_id: str, cmd: Command) -> None: ...

class JsonFileStorage(Storage):      # 第一期：本地 JSON 文件
    ...

class MemoryStorage(Storage):        # 测试用：内存
    ...

# 未来：
# class RedisStorage(Storage): ...
# class PostgresStorage(Storage): ...
```

**引擎只依赖 `Storage` 接口，不知道背后是文件还是数据库。**

| 现在 | 未来多人 |
|---|---|
| `JsonFileStorage` | `RedisStorage` / `PostgresStorage` |
| 一个 `game_id` = 一个文件 | 一张表，按 `game_id` 分行 |
| 单进程 | 多进程，存储要带**乐观锁**（版本号） |

> **多人存储的关键差异**：**要防并发覆盖。**
> 建议现在就给状态加 `revision: int`，每次 `advance` +1。
> 保存时检查 `WHERE revision = 读出来的revision`，不匹配就拒绝。
> **单人时这个字段恒为递增，无害；多人时它就是并发控制。**

## 六、模式五：同时回合（Simultaneous Turns）

**这是你游戏多人化的真正形态。**

### 6.1 问题

四个人各经营一个区域，同一季度**同时**提交计划。谁先算？

### 6.2 业界做法：分阶段屏障

```
┌─────────────┐
│ 阶段1: 收集  │  等所有玩家提交计划（或超时）
└─────────────┘
       ↓  ★ 屏障：所有人到齐才继续
┌─────────────┐
│ 阶段2: 结算  │  服务端统一算（一次，不是每人一次）
└─────────────┘
       ↓
┌─────────────┐
│ 阶段3: 广播  │  把新状态发给所有人
└─────────────┘
```

**你的 `advance(plans: Dict[player_id, Plan])` 已经是这个形状了** ——
它收齐所有计划再一起算，**正是阶段1→阶段2的屏障**。

> 这就是为什么那条红线（收齐 plans 再结算）这么重要：
> **它不是为了单人，是为了多人时的"同时"。**

### 6.3 共享资源怎么分

多人同时买同一批货，供给不够怎么办？

**你的红线 4 已经预留了**：

```python
def allocate_proportional(demand, supply): ...   # 按比例
def allocate_fcfs(demand, supply): ...           # 先到先得
def allocate_auction(demand, supply): ...        # 竞价
```

**现在单人时，`demand` 只有一个键，怎么分都等价。**
多人时换个函数即可。

## 七、把这些串起来：完整架构

```
┌───────────────────────────────────────────────────┐
│  web/  前端                                        │
│  · 只发命令（POST /command）                        │
│  · 只显示状态（GET /state）                          │
│  · 零计算 ★                                        │
└───────────────────────────────────────────────────┘
                    ↕ HTTP (JSON)
┌───────────────────────────────────────────────────┐
│  server/  服务层                                    │
│  · 校验命令（不信客户端）★                           │
│  · 收齐所有玩家 plan  → 调 advance()                 │
│  · 广播新状态                                       │
└───────────────────────────────────────────────────┘
                    ↕ 函数调用
┌───────────────────────────────────────────────────┐
│  engine/  引擎 ★ 全部业务逻辑                        │
│  · advance(state, plans)  ← 纯函数、确定性           │
│  · apply_command(state, cmd)                        │
│  · 不 import server                                 │
│  · 不碰文件、不用随机、不用 datetime ★               │
└───────────────────────────────────────────────────┘
                    ↕ 读
┌───────────────────────────────────────────────────┐
│  config/config.json                                 │
└───────────────────────────────────────────────────┘
                    ↕ Storage 接口（可替换）
┌───────────────────────────────────────────────────┐
│  storage/                                           │
│  第一期: JsonFileStorage                            │
│  未来:   Redis / Postgres（同接口）                  │
└───────────────────────────────────────────────────┘
```

## 八、现在就该做的 / 明确现在不做的

### ✅ 现在就该做（成本低、未来收益大）

| # | 做法 | 成本 | 收益 |
|---|---|---|---|
| 1 | **`Plan` 改叫"命令集合"**，每个操作是一个可序列化的 Command | 低 | 多人/回放/AI 托管 |
| 2 | **加 `command_log`** 到存档 | 极低 | 调试 + 回放 + 审计 |
| 3 | **`Storage` 抽象成接口** | 低 | 换存储不动引擎 |
| 4 | **状态加 `revision` 版本号** | 极低 | 未来并发控制 |
| 5 | **引擎保持确定性**（不用 random / datetime） | 零 | 可重放、可测试 |
| 6 | **服务端权威**（校验在前端之外） | 低 | 多人必需 |

### ❌ 现在明确不做

| 不做 | 何时做 |
|---|---|
| 真正的网络同步 / WebSocket | 要做多人时 |
| 数据库 | 存档变大或要多人时 |
| 并发锁 / 乐观锁实现 | 多人时（但**字段先留**） |
| 匹配 / 房间 / 大厅 | 多人时 |
| 断线重连 | 多人时 |

## 十、一句话总结

### 你的两个问题

**Q1：存储框架要能适配未来多人？**

> **要。做法：把 `Storage` 抽象成接口 + 加 `command_log` + 给状态加 `revision`。**
> 三条成本都很低，但现在不做，以后要动引擎。

**Q2：架构本身有没有可借鉴的？**

> **有，而且是成熟领域。你的游戏属于"回合制 + 命令 + 服务端权威 + 确定性模拟"这一族。**
> **最该抄的三个模式**：
> 1. **Command Pattern** —— 所有操作变成可序列化对象（[出处](https://gameprogrammingpatterns.com/command.html)）
> 2. **纯函数状态更新** —— 保证确定性，可重放（[boardgame.io](https://github.com/boardgameio/boardgame.io)）
> 3. **分阶段屏障** —— 收齐所有玩家再结算，**你的 `advance(plans)` 已经是了**
>
> **参考实现看 [boardgame.io](https://github.com/boardgameio/boardgame.io)（架构同族），理论看 [Game Programming Patterns](https://gameprogrammingpatterns.com/command.html)。**

### 最后

> **你之前那五条红线，其实就是这套架构的简化版。**
> `advance(plans)` = 分阶段屏障
> `allocator` = 共享资源分配策略
> `player_id` 索引 = 状态分区
> "服务层只转发" = 服务端权威
>
> **你凭直觉定的规则，和业界成熟做法是对上的。** 现在只是给它们配上名字和更细的实现。
