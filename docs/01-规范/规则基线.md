## 0. 一页话讲清这个程序是什么

**输入**：一份 `config.json`（配方 + 价格 + 工资）＋ 每季度的玩家计划。
**输出**：新的现金、地块状态、市场价格、财报数字（**没有库存** —— 没有仓库）。
**性质**：一台确定性的账本机器。同样的输入必须得到同样的输出。

一条铁律（架构级，不可动摇）：

> **程序决定事实，AI 只负责解释。**
> 生产 / 成本 / 价格 / 成交 / 税收 / 处罚 = 程序。
> 财报解读 / 新闻 / 合同起草 / 政策说明 = AI。
> **AI 不得改规则、造补贴、改价格、定处罚。**

**三类地块，三套逻辑（本轮明确）**：

| 类别 | 逻辑 | 产出 |
|---|---|---|
| 农业 / 资源 / 工业 | **有产品**：原料 + c + d → 产量 e，进全国市场卖 | 商品 |
| 服务 | **无产品（0→0）**：烧资金，给邻居加成（任何邻居都算，率按自身等级 5%/7.5%/10%） | 只出资金 |
| 研究 | **无产品**：烧资金、出效率加成（+1%/块，封顶 +3%） | 只出效率 |

## 1. 核心数据模型（程序要建的对象）

```
GameState
├── world                      # 共享层（所有玩家可见）
│   ├── quarter: int           # 世界时钟，从 1 开始
│   ├── policies: [Policy]     # 生效中的政策
│   └── price_history: {goods: [float]}   # 上期价，供【结算时按上季价记账买入】用
├── market                     # 共享层：每商品一条供需曲线参数
│   └── goods: {gid: {P0, Q0, Es, Ed, P_min}}
└── players: {"p1": PlayerState, ...}     # 私有层，一律按 player_id 索引
    └── PlayerState
        ├── cash: float
        ├── plots: {plot_id: Plot}        # 地块，含类型/等级/状态/磨合计数
        ├── inventory: {goods: qty}       # ★ 没有仓库 → 通常为空，见 §11.1
        ├── debts: [Debt]
        └── credit_flag: bool             # 失信标记
```

**第一期范围（已拍板，不得含糊）**：

> **功能上只做单人发展 —— 一局一个玩家，不做联机、不做网络同步、不做请求排队。**
> **但代码结构必须按多人建模，把接口留住 —— 以后加联机时，引擎核心一行不改，只在外层套一层"服务器 + 请求队列"壳。**

一句话原则：**数据结构按多人设计，引擎实现按单玩家跑。**

### 1.1 五条写法红线（违反任何一条，以后加联机＝重写）

| # | 红线 | ✅ 这样写 | ❌ 不要这样 |
|---|---|---|---|
| 1 | **玩家身份永远用 `player_id` 索引** | `state["players"]["p1"]["cash"]`<br>`def produce(state, player_id, plot_id)` | `state["cash"]`<br>`def produce(state, plot_id)` |
| 2 | **共享 vs 私有分层** | 共享：市场价 / 供需曲线 / 政策 / 世界时钟<br>私有：现金 / 地块 / 库存 / 债务 / 研究 | 把现金和市场价格塞进同一个 dict |
| 3 | **季度推进收齐所有计划再一起结算** | `def advance(state, plans: Dict[PlayerId, Plan])` | `def advance(state, plan)` |
| 4 | **共享资源的分配规则做成可替换策略函数** | `allocator: Callable` 注入，默认"按比例" | 在 `market.py` 里写死"先到先得" |
| 5 | **服务层只转发、不放规则** | `POST /state?player=p1` | 在路由里算价格或改状态 |

**第 1 条最贵**：把玩家状态摊在顶层，以后要改成多人几乎等于重写。**从第一行代码就守住。**

### 1.2 对照代码骨架

```python
def settle_market(state, allocation_strategy=allocate_proportional): ...
```

### 1.3 现在不做的（真到做多人时才碰，别提前写）

| 不做 | 原因 |
|---|---|
| 服务器持全局状态 | 单机期状态就在本地，套壳时再挪 |
| 网络同步 / 断线重连 | 无网络层 |
| 两边时钟一致 | 单机只有一个时钟 |
| 玩家间实时竞价 | 第一期只有一个人，市场是"玩家 vs 系统" |
| **并发结算** | **见下方 §1.3.1 —— 用串行锁消掉，不是"不做"而是"用最简单的办法挡掉"** |

**注意**：不做上面这些，**不代表**可以违反 §1.1。两者是不同层次的事——上面是"没有的功能"，§1.1 是"已有的写法"。

#### 1.3.1 限制并发（✅ 2026-10-16 定案）

**服务层对同一局只允许一个请求在跑，全部串行。**

```
同一 game_id 上：一个请求进 → 拿锁 → 算完 → 释放 → 下一个才能进
```

| 为什么需要 | 说明 |
|---|---|
| `advance()` 会整体改写状态 | 两个请求同时跑 = 状态被交叉覆盖，账必错 |
| 结算必须"一次算完" | 中途被打断会留下半个季度，比崩溃更难查 |
| 不用复杂方案 | **第一阶段就是一把锁**，不要乐观锁 / 版本号 / 事件溯源 |

**落地要点（四条）**：

| # | 规则 |
|---|---|
| 1 | **锁的粒度是"每局一把"**（`game_id` → `Lock`），不是全局一把——不同局互不阻塞 |
| 2 | **提交计划也走串行**：`plans` 只增不改，配合锁天然满足"一个玩家只能提交一次" |
| 3 | **单人期 `len(plans)==1` 立即结算**，锁内完成，不留等待态 |
| 4 | **锁在 `try/finally` 里释放**，异常也必须放锁，否则整局卡死 |

> ⚠️ **不在引擎里做锁**。`engine/` 是纯函数，**不知道锁的存在**；
> 锁只活在服务层（`server/session.py`）。这样引擎仍能脱离 Web 单独跑。
>
> ⚠️ **这不是"防并发写库"那类问题**（《项目架构-总》§八已澄清：行动阶段是收集、结算是单点触发）。
> 这里挡的是**同一个 HTTP 端点被重复点两次 / 重放**，属于最朴素的一类并发。

## 2. 配置层：配方与商品

### 2.1 配方字段（✅ 已定）

每条配方记录五个字段，**含义已锁死，这是所有数值校准的地基**：

| 字段 | 含义 |
|---|---|
| 商品投入 | **基准满负荷一个季度**消耗的实物数量（不是生产 1 单位的投入） |
| 经营费 `c` | 不含商品采购、不含工资的经营现金费用（维护 / 能源 / 外购服务） |
| 劳动 `d` | 基准满负荷季度占用的劳动量 |
| 产量 `e` | 基准满负荷季度产出 |

> ⚠️ 这句话必须写进文档首行：**a、b、c、d、e 是"一季度生产 e 单位产品"的整批投入。** 队友若对此有不同理解，全套价格必须重算。

### 2.2 商品清单与合并规则（✅ 已定）

- `A B C D` 农产品、`F` 资源原料、`G` 工业基础材料、`H-A/H-F/H-G/H-J` 四类机械、`I` 高技术产品、`H-A+/H-F+/H-G+/H-J+` 四类自动化机械。
- **不同等级共用同一商品编码，只改配方**：一级/二级/三级农业都产出 `A`，市场上同价。升级的收益来自产量与单位成本，**不是来自一个更低的售价**。
- 由此 **不要** 建 `A2/A3/B2/B3/C2/C3/D2/D3/F2/F3` 独立市场——这些旧编码作废。
- `J` **已不是商品**：服务地块 0→0 没有产出，因此不建独立市场、不进仓库、不可出口。旧编码 `J/J2/J3` 全部作废。

## 3. 计算层：每个季度到底算哪些式子

### 3.1 效率 E（✅ 结构已定，⚠️ 一处数值待确认）

```
E = E_邻接 × E_幸福 × E_磨合 × (1 + 研究加成)
```

**乘法关系，不是加法**——这是防止效率重复放大的关键。

| 分量 | 规则 | 状态 |
|---|---|---|
| `E_邻接` | 八邻格；按**关联表**判定，每个关联邻居 +5%，上限 +40%；升级/在建/未运行地块不提供加成 | ✅ 表已给（见 §3.2） |
| `E_幸福` | 使用**上一季**幸福度 H（0–1 连续量），映射到 0.9–1.1 | ✅ 公式已给（见 §3.3.5） |
| `E_磨合` | 首个可用季度 0.5，第二季 0.75，第三季起 1.0 | ✅ |
| 研究加成 | 每块正常运行的研究地块 +1%，同一玩家上限 +3%；不对研究地块自身加成 | ✅ |

### 3.2 邻接加成表（✅ 已定，按关联表判定）

**判定原则（已拍板）：不只有同类型地块有增益。** 相邻地块只要落在该地块的"关联地块类型"里，就算一个关联邻居，每个 +5%。

| 地块类型 | 关联地块类型 | 每邻居 | 上限 |
|---|---|---|---:|
| 农业 | 农业、资源 | +5% | +40% |
| 资源 | 资源、工业 | +5% | +40% |
| 工业 | 工业、资源 | +5% | +40% |
| 服务 | 服务、农业、工业 | +5% | +40% |
| 研究 | 工业、高技术 | +5% | +40% |

```
E_邻接 = 1 + min(0.05 × (关联邻居个数), 0.40)
```

例：一块农业地块周围有 1 块农业 + 2 块资源 → 3 个关联邻居 → `E_邻接 = 1.15`。

**通用规则（服务地块除外，见 §3.6）**：只有关联邻居提供加成，非关联邻居（如农业挨着服务）不计。

> 注：服务地块的邻接规则是本表的一个例外——**任何**邻接地块都给它 10%，见 §3.6。编码时服务要单独分支。

### 3.3 人口 / 粮食需求 / 幸福度（✅ 本轮新定 —— 取代旧的"固定人口"方案）

> **本节覆盖旧规则**：旧版"人口固定 100、不加权、幸福度由满足率+覆盖率合成"作废。
> 人口变量**保留为状态**，第一期用下面这套机制驱动它。

#### 3.3.1 人口由岗位数推出（✅）

```
L = Σ(所有开工地块的 d × u)        岗位数 = 实际雇用的劳动量
N = L × r                          人口，r = 2（常数：总人口 / 劳动力比例）
```

> ⚠️ **不取整（2026-10-16 定案，取消 `round`）**：`L` 与 `N` 都**保留小数**。
> 理由见下方"为什么 `L` 本身就会是小数"。

**含义**：你开发的地块越多、开工越足，雇的人越多，区域人口越大。人口**不是外生给定，而是内生结果**。

##### 为什么 `L` 本身就会是小数（✅ 澄清，不是 bug）

`L` **不是"几块地"，而是"这季实际雇了多少劳动量"**。两个来源都会让它带小数：

| 来源 | 例子 |
|---|---|
| **`u` 是 0–1 的比例** | 一块 1 级农业 `d=2`，半开工 `u=0.5` → `L = 2 × 0.5 = 1` |
| **`d` 本身就是小数** | 一块 3 级农业 `d=1.5`，满负荷 `u=1` → `L = 1.5` |

配方里三级地块的 `d` 大量是 `1.5 / 2.5`（见 §2.3），所以**即使全部满负荷开工，`L` 也天然带小数**。

> **这不是"人口可以是半个人"**，而是 `d` 的口径是**劳动投入当量**而非人头数。
> **引擎一律存小数**（否则账对不上），**显示层负责取整或取一位小数**（界面上不出现"1.5 人"）。
>
> ⚠️ **待调数值**：若希望 `L` 恒为整数，要改的是**配方里的 `d`**（全改整数）与 **`u` 的粒度**（只允许 0/1），
> **不是加一个 `round` 去掩盖它**。这条列在 §9 的待调项里，不改配方。

##### 全文不再需要任何 `round`（✅）

取消 `N` 的取整后，**本项目的计算链上不存在任何四舍五入**：`L / N / ḡ / m / F / H / E / P_t` 全部是连续量，一路小数算到底。
唯一涉及"取整"的地方是**显示层**（前端把 `N=5.0` 画成 `5 人`）——那是 UI 的事，与规则无关。

| 岗位 L | 人口 N | 基础篮位数 N/5 |
|---:|---:|---:|
| 3 | 6 | 1.2 |
| 5 | 10 | 2.0 |
| 11 | 22 | 4.4 |
| 25 | 50 | 10.0 |
| 50 | 100 | 20.0 |

> **`r = 2` 已定案**（先符合客观现实；后续数值调节另议）。
> 旧基线那个"N=100、D=20 篮子、A8/B4/C2/D0.4"需 **50 个岗位**才达到，属中后期规模。
> **M1 两块地各 d=3 → L=3 → N=6**，不是 100。详见 §8.1。

#### 3.3.2 地块等级乘数（✅）

```
ḡ = 所有**开工地块**的平均等级
    —— 含农业/资源/工业/服务/研究全部类型（这些地块都有岗位）
    —— 不含 0 级空地、在建地块
m = 1 + 0.15 × (ḡ − 1)              等级越高，居民吃得越好
```

| ḡ | 1.0 | 1.5 | 2.0 | 2.5 | 3.0 |
|---|---:|---:|---:|---:|---:|
| m | 1.000 | 1.075 | 1.150 | 1.225 | **1.300** |

**为什么要这个乘数**：产业升级后居民生活水平应随之提高，粮食需求上升——这是"发展带来压力"的正反馈来源。

#### 3.3.3 两档粮食需求（✅ —— 基准与优秀用**不同**的商品集合）

```
F_基准 = (N / 5) × m             必须达到，达标才给 0.6 幸福度
F_优秀 = 1.5 × F_基准            达到才给 1.0 幸福度
```

**关键：两档需要的商品不一样。**

| 档位 | 需要哪些商品 | 说明 |
|---|---|---|
| **基准** | **A、B** | 口粮。**A 与 B 必须都有、且可互相替换** |
| **优秀** | **A、B、C、D** | 生活品质。**四样都要** |

**基准档的"必须且可替换"怎么算**（✅）：

```
需求总量  R = F_基准 × (0.4 + 0.2) = 0.6 × F_基准       A、B 的合计口粮
实际供给  S = min(A_投放, 0.4×F_基准) + min(B_投放, 0.2×F_基准)
```

- **必须**：A、B 各自都要有。若 `A_投放 = 0` 或 `B_投放 = 0`，基准档**不成立**（单靠一样顶不上）。
- **可替换**：在各自上限内，A 多了能补 B 的缺口，反之亦然。`S` 取到 `R` 即基准达标。

**优秀档**：A/B/C/D **四样都需要满足各自配额**（`0.4 / 0.2 / 0.1 / 0.02` 比例），任缺一样则不达优秀。

#### 3.3.4 幸福度 = 平滑上升（✅ 中间段**线性**，斜率已算）

设 `F` = 实际达成的等效篮位数：

```
H = 0.6 × (F / F_基准)                               , F < F_基准
H = 0.6 + 0.4 × (F − F_基准) / (F_优秀 − F_基准)     , F_基准 ≤ F < F_优秀
H = 1.0                                              , F ≥ F_优秀
```

##### ★ 两段直线的斜率（2026-10-16 确认：中间线性）

因为 `F_优秀 = 1.5 × F_基准`，所以 `F_优秀 − F_基准 = 0.5 × F_基准`，中段斜率可以化简：

| 段 | 范围 | 斜率 | 化简后 |
|---|---|---|---|
| **下段**（还没吃饱） | `0 → F_基准` | `0.6 / F_基准` | — |
| **中段**（吃饱→吃好） | `F_基准 → F_优秀` | `0.4 / (0.5 × F_基准)` | **`0.8 / F_基准`** |
| **上段**（吃好以上） | `≥ F_优秀` | `0`（封顶 1.00） | — |

> **中段斜率是下段的 4/3**（`0.8 / 0.6 = 4/3 ≈ 1.333`）。
> 含义：从"吃饱"往"吃好"推，**每一份粮换来的幸福度比"从饿到饱"更值钱**——
> 这是有意让"冲优秀档"值得投入。

**中段的两个端点**：`(F_基准, 0.60)` → `(F_优秀, 1.00)`，**直线连接，中间不拐弯**。

**斜率表（算例）**：

| `F_基准` | `F_优秀` | 下段斜率 | 中段斜率 |
|---:|---:|---:|---:|
| 1.2 | 1.8 | 0.500 | **0.667** |
| 2.0 | 3.0 | 0.300 | **0.400** |
| 4.0 | 6.0 | 0.150 | **0.200** |
| 10.0 | 15.0 | 0.060 | **0.080** |

> 例：`F_基准 = 2.0` 时，中段从 `(2.0, 0.60)` 直线到 `(3.0, 1.00)`，
> 斜率 `0.40`。取中点 `F = 2.5` → `H = 0.80`。

| F / F_基准 | 0 | 0.5 | 0.8 | **1.0** | 1.2 | **1.5** | 2.0 |
|---|---:|---:|---:|---:|---:|---:|---:|
| H | 0.00 | 0.30 | 0.48 | **0.60** | 0.76 | **1.00** | 1.00 |

**关键锚点**：`F = F_基准` → H = 0.60；`F = F_优秀` → H = 1.00；中间**直线**连接。

#### 3.3.5 幸福度 → 效率（✅）

**初始值**：第一季没有"上季 H"，取 `H₀ = 0.6`（即开局 `E_幸福 = 0.90`）。**已确认。**


```
E_幸福 = 0.90 + (H − 0.6) × 0.5        , H ≥ 0.6
E_幸福 = 0.90                          , H < 0.6
```

| H | 0.60 | 0.70 | 0.80 | 0.90 | 1.00 |
|---|---:|---:|---:|---:|---:|
| `E_幸福` | 0.90 | 0.95 | 1.00 | 1.05 | **1.10** |

**与旧表的差别**：旧表是"幸福度 0–100 分档查表"，现在 H 直接是 0–1 的连续量，效率 0.9–1.1 连续插值。**旧的分档表作废**，但**端点值 0.90 / 1.10 完全一致**。

#### 3.3.6 粮食结算（✅ —— 在结算时扣，且是玩家主动选择）

> **关键时序**：粮食**不在期初扣，在结算时扣**。
> 期初是玩家**支配资金**的阶段——他可以自己决定这一季要不要花钱买粮、买多少、要不要冲优秀档。
> 系统**不预先代扣**，也不强制玩家满足粮食需求。**买不买、买多少，是玩家的经营决策。**

> **服务地块不参与粮食循环（✅ 2026-10-16 定案）**：
> **服务地块既不提供食物、也不消耗食物。** 它 0→0，纯资金流，与 A/B/C/D 完全无关。
> 也就是说：`F_基准 / F_优秀` 的判定与扣减，**只跟非服务地块产生的居民需求有关**。

> ★ **口粮只能来自买入（2026-10-16）**：因为没有仓库，**本季产出 100% 是市场供给、
> 不能拿来吃**。玩家要让居民吃上饭，必须在 `purchases` 里申报买 A/B/C/D。
> 一个只种地、不买粮的玩家 → 居民没得吃 → `H = 0`。
>
> 买了但居民没吃完的部分 → **丢弃**（不产生收入、不结转）。

**结算动作**（市场卖出之后）：

```
① 数出玩家手上可用于吃的 A/B/C/D
② 判定基准档：A、B 都必须有
     S = min(A, 0.4×F_基准) + min(B, 0.2×F_基准)
     S ≥ 0.6×F_基准 → 基准达标
③ 判定优秀档：A/B/C/D 四样配额齐全 → 优秀达标
④ 扣减：有多少扣多少，不足扣光，不欠账
⑤ 由实际达成量算 H（§3.3.4）
```

> **注意**：`F_基准` 只由**非服务地块**的岗位推出（服务不吃粮）。
> 把服务地块的 `d` 从 `L` 里剔掉，是本节唯一需要按类型分支的地方。

| 情况 | 扣减 | H |
|---|---|---|
| 达到优秀 | 扣满 A/B/C/D 配额 | 1.00 |
| 只达到基准 | 扣 A、B（按配额） | 0.60 |
| 部分达到 | **扣光手上所有能吃的** | `0.6 × 实际/F_基准` |
| 完全不投 | 扣 0 | 0.00 |

**食物不够会直接压低下季效率**——这是本机制的核心惩罚回路。**没有"只扣到基准线就停"这回事。**

**粮食扣减计入 GDP 中间投入**（居民消费实际消耗了商品）。

## 4. 市场层

### 4.1 全国商品市场（✅ 算法已定）

每商品独立一条曲线：

```
S_外(P) = max(0, Q0 + s(P − P0))
D_外(P) = max(0, Q0 − d(P − P0))
s = Es × Q0 / P0        d = |Ed| × Q0 / P0
```

程序**用原始弹性算斜率，不手工维护四舍五入后的数**。

玩家侧：`B_t` = 本季**全部买入量**（见下方定义）；`X_t` = 本季**全部卖出量**。求价令 `S_外 + X_t = D_外 + B_t`，在线性有效区间内：

```
P_t = P0 + (B_t − X_t) / (s + d)
```

##### ★ `X_t` = 本季产出（没有仓库，不用申报）✅ 2026-10-16 拍板

用户原话：**"玩家不需要申报要卖，因为没有仓库，生产出来的就是'供'本身。"**

```
X_t = 本季全部产出 − 合同交付量
```

| 由此定死的事 | 说明 |
|---|---|
| **不需要"申报卖出"** | 产出自动全部成为市场供给 |
| **没有"季末清仓"** | 没有仓库就没有库存可清（旧 §11.1 作废） |
| **产出不能拿来吃** | 它已经全部是市场供给；居民口粮只能从 `purchases` 买 |
| **唯一例外是合同** | 玩家间协议、低于市场价，见下 |

> ⚠️ 这条把上一版"预估清仓量并进 `X_t`"的整套推导**取消了**——
> 清仓这个概念本身不存在了，`X_t` 直接等于产出，没有任何需要推算的余地。

##### ★ 合同通道（保留口子，第一期不实现）

用户原话：**"要保留一个额外的通道，之后玩家间可以通过协议低于市场价提供，
这个需要到时候能实现。"**

没有仓库之后产出 100% 自动进公开市场，于是"**我想把货便宜卖给隔壁老王**"
这件事没有地方表达 —— **合同就是这个唯一的例外通道**。

对求价的影响（两条都要扣，否则合同会凭空扰动市场）：

```
卖方：X_t = 本季产出 − 合同交付量      ← 货没进公开市场，不该压价
买方：B_t = 采购量   − 合同收货量      ← 货不是从公开市场买的，不该抬价
```

合同价由**双方协商**、**低于市场价**，不走 `P_t`。

> 接口已留：`Plan.contracts`（`ContractAction` 已有 action / counterparty /
> goods / qty / price 字段）+ `pipeline._contract_deliveries()`。
> **第一期该函数明确报错**而非静默忽略 —— 忽略会让玩家以为货交出去了。

#### 交割时序与扣款（✅ 2026-10-16 定案 —— 本条足够权威，覆盖此前所有冲突写法）

**两步，不要混：**

| 步骤 | 时点 | 用哪个价 | 做什么 |
|---|---|---|---|
| **① 买入（记账）** | 玩家操作后、**结算时** | **上一季度结算出来的价格** | 把本季所需物资按上季价**记账买入** |
| **② 卖出** | 结算时 | **本季求出的 `P_t`** | 本季产出按本期价卖出 |

**关键连锁**：①的买入量**要加进②的需求侧**——也就是说，**买货这个动作本身会把本季价格顶上去**，代价在季末体现。

```
季初无货 → 玩家申报需求（原料 + 建设物资 + 口粮）
              ↓
      B_t = 生产原料 + 建设物资 + 居民口粮       ← 三段全部计入
              ↓
      P_t = P0 + (B_t − X_t)/(s+d)             ← 买入量顶高本季价
              ↓
      卖出按 P_t；买入按【上季价】——两者价差就是交割成本
```

**为什么这个闭环自洽**：买入锁在旧价、卖出随新价。买入越多 → 本季 `P_t` 越高 → 但你的货是在**上季价**上拿的。这天然惩罚"无脑囤货"，又给了"提前锁价"的真实市场味道。

> ⚠️ **`B_t` 明确包含三段，缺一不可**：**生产原料 + 建设物资 + 居民口粮**。
> 建设物资是**一次性**买入但**同样扰动市场**——买机械建厂会让机械变贵。
>
> ⚠️ **首季没有"上季价"** → 用参考价 `P0` 兜底（§8.1 的 M1 初始条件即如此）。
>
> ⚠️ **买入的"记账时点"是结算，不是期初**：玩家在行动阶段**只是写意愿，不扣钱、不锁价、不动账户**（见 §6 第 4 步）。
> 严格说这是"**结算时按上季价买入**"——"期初买"是口语说法，落点是价格用的是上季那个价。

**价格下限**：`P_min = 0.1 × P0`。到下限仍供过于求时，**按可实现需求量分配成交，不保证全量收购**；未售商品清理，不产生收入。

> ⚠️ 程序不能只把负价格截成正数，然后仍让全部产量成交。

**接受的简化（写进文档防止队友误解）**：期初正常采购默认有全国流通供应；季内价格风险由未建模的流通部门承担；不模拟其资产负债与库存；**禁止无限买入后立即转卖的投机指令**。

### 4.2 服务不是商品市场（✅ 本轮已重定义）

**服务没有"生产 J、卖 J"这回事。** 服务地块 0→0：不产出商品，只消耗资金、产出资金。因此：

- 不建服务市场、没有 `P_J` 定价、没有"服务成交量"这个商品概念；
- 旧公式 `q_售 = min(q, 90n)`、`P_J = 400n/(16n+q_售)` **作废**；
- 服务地块的收入 = 它从居民端收到的服务费（见 §4.4）。

**但服务的"覆盖能力"仍然存在**，本来要作为幸福度指标（§3.3）的输入；**第一期不接入**（服务 0→0 后能力量未定，见 §9 A2）。服务地块的**能力**由其等级、效率与开工比例决定，这是"它能服务多少人口的篮子"，属于**能力量**，不是商品产量。

### 4.3 居民粮食结算（✅ 本轮重写，与新 §3.3 对齐）

结算时**必须实际扣除粮食**。权威公式在 **§3.3**，这里只讲结算动作。

#### 4.3.1 结算链

```
岗位 L = Σ(d × u)  →  N = L × 2
        ↓
gbar = 全部开工地块平均等级（含服务/研究）  →  m = 1 + 0.15(gbar-1)
        ↓
F_基准 = (N/5) × m        F_优秀 = 1.5 × F_基准
        ↓
基准档判定：A、B 都必须有；在各自配额内可互换 → 得 F_base_达成
优秀档判定：A/B/C/D 四样配额齐全            → 得 F_good_达成
        ↓
扣减（有多少扣多少，不足扣光）：
   基准档 A≤0.4×F_基准、B≤0.2×F_基准
   优秀档 再加 C≤0.1×F、D≤0.02×F
        ↓
H = 由 F_达成/F_基准 与 /F_优秀 平滑插值   （§3.3.4）
        ↓
E_幸福 = 0.90 + (H-0.6)×0.5               （§3.3.5）
```

#### 4.3.2 扣减表（✅ 标定锚点：N=100、gbar=1.0）

以 `r = 2`、`N = 10`（5 个岗位、全部一级地块）为例：`F_基准 = 2.0`、`F_优秀 = 3.0`。

| 档位 | 篮位数 | A | B | C | D |
|---|---:|---:|---:|---:|---:|
| **基准** F_基准 | 2.0 | **0.80** | **0.40** | — | — |
| **优秀** F_优秀 | 3.0 | **1.20** | **0.60** | **0.30** | **0.06** |

> **注意 C、D 只在优秀档出现。** 基准档（吃饱）只要 A、B；优秀档（吃好）才要 C、D。
> **旧基线的 A8/B4/C2/D0.4** 现在对应 `N=100`（岗位 50、全部一级地块），属中后期规模，不再是开局常数。

#### 4.3.3 只有家庭一个渠道（✅ 已定）

**服务地块不代购 A/B/C/D。** 服务是纯资金流 0→0，不碰物资。

所以居民粮食只有**一个渠道**：**家庭自购**。

```
居民粮食消耗 = F × 篮子配比        家庭自购，玩家期初决定买多少
服务地块      = 不采购任何物资
```

> 旧《食物关系》里的"渠道①服务地块代为采购"**作废**。

#### 4.3.4 粮食进 GDP 中间投入（✅）

| 项目 | 是否计入 GDP 中间投入 |
|---|---|
| 家庭自购的 A/B/C/D | **扣**（居民消费实际消耗了商品） |

与 §7.5 一致：`增加值 = 有效产出价值 − 实际消耗的中间投入价值`。

#### 4.3.5 时序约束（✅）

**粮食扣减在结算时做，不在期初。** 期初是玩家支配资金的阶段，买不买粮是玩家的主动决策。

结算时按当时手上剩余的 A/B/C/D 数量扣减。

> ⚠️ **与生产的关系（2026-10-16 改）：产出不能拿来吃。**
> 旧版写"卖不完的可以吃"——那是**有仓库**时代的说法。现在产出 100% 是市场供给，
> 居民口粮**只能从本季买入的 A/B/C/D 里出**。

#### 4.3.6 粮食与幸福度的因果关系（✅）

```
粮食投放量 → 幸福度 H → 下季效率 E_幸福
```

**单向。** 幸福度是**结果**，不是粮食需求的输入。避免循环依赖。

> 与旧版的差别：旧版"食物消耗不随幸福度变化"仍成立，但**旧版那句"只随人口变化"已不准确**——现在 `F_基准` 同时受人口 N **和**地块平均等级 gbar 影响。

#### 4.3.7 预算公式（⚠️ 第一期不使用）

```
B_t = 2N + (1 - tau) × W_{t-1}      W_{t-1} = 上季付给本地居民的工资
```

旧的 `D_实 = min(D, B/k)` 预算约束**第一期完全不使用**。粮食需求只看 N 与 gbar；服务费受居民规模 N 限制。`B_t` 公式**暂时搁置**。

### 4.4 服务地块：纯基础设施（✅ 已拍板 —— 本轮改定）

> **服务不产生收入。它是一块"基础设施"：烧钱，换取对邻接地块的效率加成。**

这条推翻了此前"服务费公式待定"的整个方向。原定的 `f(...)`、`Q_能力`、服务费单价**全部作废**。

#### 服务的定位

```
服务地块 = 花钱买效率的设施
  支出：营业费 0.7c + 0.3c×u×E   +   工资 d×u×16
  收入：0
  回报：给邻接地块加成（任何邻居都算，率按自身等级 5%/7.5%/10%，§3.6）——收益体现在【别的地块的产量】上
```

**为什么这么定**（三条理由）：

1. **它本来就已经有回报了。** 服务的邻接加成（任何邻居都算，率按自身等级 5%/7.5%/10%）会体现在农业/工业的产出上。再加一份"服务费收入"是**同一份价值收两次钱**。
2. **原公式的两个毛病无法靠调价修掉。** 用 `Q` 当上限时，小区域里 1/2/3 级服务收益完全相同（`N=10` 时都被 `N/5=2` 卡住），升级毫无意义；而调高单价又会让大区域服务暴利。**结构性问题，不是数值问题。**
3. **定位更清爽。** 服务是"配套"，不是"产业"。玩家建服务是在**投资自己区域的生产力**，不是在建一条赚钱的产线。

#### 对幸福感的影响

**服务不再进入幸福度。** 幸福度**只由粮食决定**（§3.3）。这与此前"A10 第一期否"一致。

> 服务覆盖率、`q_售`、`Q_能力`、`D_实` 这些中间量**全部作废**，代码里不要出现。

#### 那玩家为什么还要建服务？

| 理由 | 说明 |
|---|---|
| **效率加成** | 每个邻接地块都算；率按自身等级 **+5% / +7.5% / +10%**，三级 8 邻居理论上 +80% |
| **不占劳动力以外的资源** | 配方无商品投入，只需要现金和劳动 |
| **开局减免** | 服务有自己的「减免名额」（§5.3），名额内新建打折 |

**权衡**：服务每季净烧 `0.7c + 0.3c·u·E + d×u×16` 的现金，换来邻接产出提升。
玩家自己要判断**这笔账划不划算**——这就是玩法。

> ⚠️ **待定**：服务邻接是否有 40% 封顶？8 邻居理论上 +80%，是否太强？（原表通用规则是 +40% 封顶）

```
新建工业 → 建造时就选好走哪条路线
升级     → 升级时选定目标产物（如二级工业选 H-A 还是 H-G）

```

|---|---|
| `Plot` 只需要一个 `product` 字段 | 状态最简，存档格式稳定 |
| 开局决策有分量 | "这块地种什么"和"放哪里"一起构成开局策略 |
| UI 简单 | **建造面板有"选产出"这一步**，建成之后**不提供"更换"入口** |

> ⚠️ **待调项**：如果实测后发现玩家强烈需要转型，再考虑加"改建"工程（会引入新的工期与成本），**第一期不做**。

### 5.3 开局福利：分类减免名额（✅ 机制已定，数值待调）

**目的：鼓励开局均衡发展，避免 All In 一种地块，同时加快发育。**

> **不引入“零级地块”概念**（原设想作废）。地图上开局直接就是可建的空地，玩家自主选择摆放位置；
> 用一条**减免规则**代替“零级地块”，实现同样目的，且不增加状态复杂度。

#### 规则

**每种地块类型各有自己的「减免名额」。开局建造时，名额内的一级地块享受折扣，名额用完恢复原价。**

```
每个类型的减免名额：{ 农业: n_农, 资源: n_资, 工业: n_工, 服务: n_服 }
名额内的「新建一级」按折扣价结算；超出名额按原价。
名额只在开局期有效（一次性）。
```

**机制要点**：

| 项 | 说明 |
|---|---|
| **名额按类型独立** | 建第 2 块农业用在农业名额上，与工业名额无关 |
| **只作用于「新建一级」** | 升级、二级以上工程不享受 |
| **只在开局吃** | 一次性判定，开局之后按原价 |
| **不可挪用** | 农业名额用不完，不能挪给工业 |

#### 为什么这样能"避免单一化"

**关键在名额有限**：

> 若农业名额只有 **2** 块，则 **All In 农业**的玩家：
> 前 2 块打折，**第 3 块起全价** —— 越集中，越早开始付全价。
>
> 而**铺开建多种类型**的玩家：每种都能吃到自己的名额，
> **总折扣更多，且发育面更宽**。

**与旧方案（按品种数给折扣率）的差别**：

| | 旧方案（已作废） | **新方案** |
|---|---|---|
| 形式 | 一个全局折扣率，随品种数升 | **每个类型一份独立名额** |
| 激励 | 建第 4 种 → **前面所有**都打折 | 每种各用各的名额 |
| 强度 | 很直接 | 稍柔，更可控 |

#### 数值（⚠️ **未定，待设计**）

**名额与折扣的具体数字全部待定。**

> ⚠️ **注意**：用户举例「农业 2 / 工业 2 / 服务 1」**只是说明机制的形状，不是定值**。
> 用户明确交代：**「具体怎么给不要参考我的这个建议。只是看这个例子。」**
> **所以不要把这组数字当默认值写进 `config.json` 或代码。**

**待定项**：

## 6. 季度执行顺序（✅ 已定：程序的"心脏"）

> **2026-10-16 重排**：此前第 4 步是"**期初**资金与采购：扣工资和经营费"。
> 现按用户裁定改为——**玩家阶段（期初）只提交 Plan，不扣钱、不锁价、不动账户**；
> **物资款 + 工资 + 经营费在结算时一次性从公用账户扣清**。
>
> 价格口径不变：**买入按上季价、卖出按本季价**（§4.1）。

| 阶段 | 执行内容 | 动不动账户 |
|---|---|---|
| 1. 期初更新与公告 | 更新项目工期；到期完工设施本季可用；发放已确定补贴；公布上期财报、价格、政策 | 只发补贴 |
| 2. 玩家确认计划 | 安排地块、开工比例、融资、**申报采购**（原料/建设物资/口粮）、工程和合同；**只校验，不执行** | ❌ 不动 |
| 3. **期初人口计算** | **算 L → N → ḡ → m → F_基准/F_优秀（供结算判定用）；上季 H 决定本季 E_幸福** | ❌ 不动 |
| 4. **生产** | 按本季地块状态、上季幸福度与效率生成产出；**生产原料在此当场消耗** | ❌ 不动 |
| 4.5 **买入汇总与求价** | **`B_t` = 生产原料 + 建设物资 + 居民口粮**；**`X_t` = 本季产出 − 合同交付**；求出本季 `P_t` | ❌ 不动 |
| 5. **一次性扣款** ★ | **物资款（按上季价）+ 工资 + 经营费**，一笔从公用账户扣清 | ✅ **唯一扣款点** |
| 6. 产品分配与工程投入 | 合同交付；本季产品投入工程 | 实物 |
| 7. 市场结算 | **产出按 `P_t` 全部卖出**（不用申报）；**销售收入到账** | ✅ 进账 |
| 7.5 **粮食结算** | **用玩家本季买入的 A/B/C/D → 判定基准档(A/B)与优秀档(A/B/C/D) → 扣减 → 得 H（§3.3.6）** | 实物 |
| 8. 税收、争议与报告 | 结算工资税，处理上报违约，更新幸福度及财报、新闻 | ✅ 进账 |
| 9. 结转 | 保存现金、设施、工程进度、债务、历史价格和**本季 H**；**季末零库存** | — |

> **改动说明（历次累积）**：
> - 服务已不是商品，没有"卖 J"这一步（服务 0→0，纯资金流）。
> - **新增 7.5 粮食结算**：粮食在结算时扣，买不买粮是玩家的主动决策。
> - **阶段 3 的位置很关键**：人口与粮食需求必须在生产之前算出。
> - **第 5 步"一次性扣款"**：物资款 + 工资 + 经营费合并，玩家阶段不扣钱。
> - ★ **本轮（2026-10-16）**：**第 7.7 步"季末清仓"整步删除** —— 没有仓库就没有库存可清（旧 §11.1 作废）。
>   `X_t` 直接等于产出，玩家**不需要申报卖出**。产出也**不能拿来吃**，口粮必须买。

**贯穿全流程的四条经济约束**（每一阶段都要检查）：

1. 资金不能超支（**在第 5 步一次性校验：物资款 + 工资 + 经营费 ≤ 现金**）；
2. 劳动力不能重复分配；
3. 同一件商品不能重复消耗或出售；
4. **本季生产出的商品，不能倒过来投入本季已经开始的生产。**

## 7. 税收 / 合同 / 信用 / GDP

### 7.1 工资税（✅ 测试参数）

`工资税 = W × 10%`。账面口径：工资支出记**税前总额**；工资税记**回流收入**；净支出 = 税后工资；**不生成居民消费订单**。

### 7.2 合同（✅ 初版范围）

支持：玩家间借贷、商品供货、双方协商延期/改价/解除。

**时间约束**：本季生产后的交货，**不能支持接收方本季已经完成的生产**。

无库存玩法时，收到的合同商品只能：用于尚未执行的本季工程，或进入本季销售；**不自动保留到下季生产**。

> ★ **2026-10-16 补充：合同是唯一的"非公开市场"通道。**
> 没有仓库之后产出 100% 自动进公开市场，所以合同成了玩家之间
> **私下按低于市场价成交**的唯一入口。对求价的影响见 §4.1：
> 卖方从 `X_t` 扣、买方从 `B_t` 扣。

### 7.3 违约与失信（✅ 流程已定）

程序记录未履约义务 → 受损方可接受、协商或上报 → 上报确认后形成赔偿或待清偿义务 → 进入政策信用状态 → 未解决的严重违约可能失去新补贴/奖励/信用支持。

**已承诺拨款不随意撤回**；完成清偿补救后按规则恢复资格。**AI 只解释和提醒，不自行判罚。**

```
增加值 = 有效产出价值 − 实际消耗的中间投入价值
```

固定统计价**使用本轮参考价，不随季度销售价变化**。工资不作为中间投入再扣；原料要扣；外购维护/能源等经营服务（即 `c`）要扣；**贷款、拨款、税款不计入**；建设与研发成果未建完整核算前**单独报告，不硬塞进 GDP**。

### 11.1 ~~季末清仓出售~~ ❌ **已作废（2026-10-16）**

> **本节整节作废**，因为**没有仓库**。
>

> | 不得"先卖光再凭空完成消费" | **产出不能吃** → 口粮必须买（见 §3.3.6） |
> | 工程预留材料不算普通库存 | 建设物资直接进工程，本就不进库存 |
>
> 唯一残留的边界情况：**买了口粮但居民没吃完** → 多余部分**丢弃**
> （不产生收入、不结转）。因为它已经不是"待售商品"，而是买错了的东西。
>

<details>
<summary>原文（已作废）</summary>

**§6 第 9 步原先只写"不保留普通待售库存"，没说这些货去哪了——是"清仓变现"，不是"蒸发"。**

```

销售收入[g]    = 出售量[g] × 价格[g]        ← 价格 = 本季求出的 P_t（§4.1）

```

> ⚠️ **清仓量必须参与本季求价**（`X_t = 申报卖出 + 清仓量`，见 §4.1）。

> 所以**求价之前先按数量把粮食扣减推算出来**（§4.3.7：扣减只看数量、不看价格）。

**不出售的对象（不是"库存预留例外"，而是本来就不是普通库存）**：

### 11.3 无效 Plan 处理（✅ 采纳为工程建议）

- 采购超限、材料不足或资金不足时**返回明确错误**；
- **不自动减少**采购或开工量；**不产生部分状态变更**；
- AI 秘书提出修改方案后，**由玩家重新确认**；
- 错误信息至少含：**错误类型 / 涉及商品或地块 / 申请值 / 可用值 / 差额**。

### 11.4 AI 秘书的边界与接口（✅ 与既有铁律一致，已确认）

**边界**：AI 秘书**只解释与规划**；**未经玩家确认**，不提交正式 Plan、不改变玩家状态、不购买、不建设、不结束季度。
引擎负责**合法性校验、精确计算、状态变更、季度结算**。

- AI **不得自行创造**配方、价格、权重或例外规则；
- 精确金额、投入数量、效率和收益预测**必须来自确定性计算器**；
- **缺失规则或数据必须明确报出**，不得以语言推测代替正式计算。

**五个接口名（采纳为服务层命名）**：

```
get_rules       查询规则和版本
get_state       查询玩家状态
validate_plan   校验方案，不改变状态
simulate_plan   试算方案，不改变状态
submit_plan     玩家确认后正式提交
```

- 试算结果应**包含规则版本及状态版本**；**正式执行前重新校验**，防止执行过期方案。
- 对应关系：`simulate_plan` = 既有的 `preview()`、`validate_plan` = `tool_validate`、`submit_plan` = 服务端 `submit`。
  **架构不变**——`preview` 与 `advance` 共用实现，**AI 永远调不到 `advance`**（见 [`AI自主演算-架构影响.md`](../03-架构/AI自主演算-架构影响.md) §6、§8）。

### 11.5 邻接计算器的可解释性字段（✅ 采纳，供 UI 使用）

计算器应能返回**每一项邻接贡献**：邻居 ID、邻居类别与等级、有效性及排除原因、单项贡献、封顶前总加成、封顶后效率。

> **关联度 / 等级权重两个字段保留为恒 1**——本项目采用 §3.2 的关联表口径，不引入该机制（见 §11.7-3）。
> 本字段集直接支撑 [`界面要显示的变量清单.md`](../04-交接/界面要显示的变量清单.md) §四（E 值展开拆解）与 §四-bis（高亮"加成的邻居/不加成的邻居"）。

### 11.6 数据纪律（✅ 采纳）

- **不得为填满配置而编造数据**；
- **历史测试数字只属于其对应规则版本**，应根据最终规则**重新生成测试预期**，**不能反向修改规则迁就旧数字**；
- **"工程建议"和"待导入数据"不得自动升级为已确认玩法**；
- **历史举例、测试条件和估算不得自动成为正式参数**；
- 市场模块配置齐全 **≠** 生产、建设、服务、幸福度也已齐全。

**1. 每季采购上限（新数据，暂不启用）**

队友给出了 15 个商品的每季采购上限：`A/B/C/D/F/G = 10000`；`H-A/H-F/H-G/H-J/I/H-A+/H-F+/H-G+/H-J+ = 1000`。

① 已选**动态曲线**，买入会把价格推高，本身即是约束；

③ 但其**合并计数口径有价值**（防同一笔重复计额度），若启用应**整套采纳**。
