## 一、先说结论

### 1. 你的项目属于哪一类

**它不是"游戏"，是一个"账本程序 + 一个界面"。**

| 看起来像 | 实际上是 |
|---|---|
| 模拟经营游戏 | 确定性状态机 |
| 需要游戏引擎 | 不需要，一行都不需要 |
| 复杂 AI | 不需要，AI 只写文案 |
| 实时渲染 | 不需要，静态格子 + 数字刷新 |

**真正的技术含量只有两处**：

1. **线性供需求交**（高中数学：两条直线求交点）
2. **一组公式的求值顺序**（先算什么后算什么）

其余全是"读数据 → 套公式 → 存结果"。

### 2. 要不要去 GitHub 找开源组件

**核心结论：不要。** 理由三条：

| 理由 | 说明 |
|---|---|
| **没有能用的** | "区域经营 + 季度结算 + 这套配方"是你自己定的规则，**世上不存在和你规则一致的开源项目** |
| **成本 > 收益** | 找一个"经济模拟引擎"，你要读懂它的抽象、适配你的规则，**比自己写慢** —— 而你的规则本身只有 200 行核心逻辑 |
| **黑客松最怕黑盒** | 用不熟的库，出 bug 时你**不知道是库的问题还是你的问题**。M1 对不上 1033.12 时，你会疯 |

**唯一值得复用的一类：通用基础设施**（HTTP 框架、序列化、测试），它们和你的游戏规则**无关**。

> **一句话**：**规则自己写，轮子用现成的。** 别用"游戏引擎"，可以用"Web 框架"。

## 二、为什么不要游戏引擎（深入一点）

### 2.1 游戏引擎解决什么问题

主流游戏引擎（Unity / Godot / Pygame / Arcade）解决的是：

| 引擎解决 | 你需要吗 |
|---|---|
| 实时渲染（60fps 画三角形） | ❌ 你是静态格子 + 数字 |
| 物理引擎（碰撞、重力） | ❌ 没有物理 |
| 动画系统（骨骼、补间） | ❌ 数字刷新即可 |
| 输入系统（手柄、键鼠时序） | ❌ 点按钮而已 |
| 场景图 / 实体组件系统 | ❌ 你的"实体"是 12 个格子 |
| 资源加载（模型、贴图） | ⚠️ 前端同学用 CSS 画格子 |

**ECS（Entity-Component-System）** 是最常被误用的：它是为了**几万个实体每帧更新**设计的。
**你只有 12 个地块、一季更新一次。** 用 ECS 是杀鸡用牛刀，而且是**一把要学三个月的牛刀**。

### 2.2 你的程序真正的形状

```
输入：config.json + 玩家操作
         ↓
    ┌─────────────────┐
    │  纯函数计算核心  │   ← 全部业务逻辑在这
    └─────────────────┘
         ↓
输出：新的 state + 一份报告
```

**关键性质：确定性（deterministic）。**

同样输入 → 永远同样输出。没有随机、没有时间依赖、没有并发。

> 这让程序**极其好测试**：喂一组输入，比对一组输出。**你已经有 M1 三个数了。**

### 2.3 所谓的"引擎"其实就是这个

```python
def advance(state, plans):
    for pid, plan in plans.items():
        apply_plan(state, pid, plan)        # 1. 应用操作
    for pid in plans:
        compute_efficiency(state, pid)      # 2. 算效率
        update_population(state, pid)       # 3. 算人口粮食
        do_purchases(state, pid, plan)      # 4. 期初采购
        run_production(state, pid, plan)    # 5. 生产
        advance_construction(state, pid)    # 6. 建设
    settle_market(state, allocator)         # 7. 市场（共享）
    for pid in plans:
        settle_food(state, pid)             # 8. 粮食结算 → H
        settle_taxes(state, pid)            # 9. 税收
    state.world.quarter += 1                # 10. 结转
    return state
```

**这就是全部。** 没有引擎，没有框架，就是一个按顺序执行的函数。

## 三、架构该怎么做（分层）

### 3.1 三层结构

```
┌──────────────────────────────────────────┐
│  web/          前端（前端同学）           │
│  只显示，零计算                            │
└──────────────────────────────────────────┘
              ↕ HTTP / JSON
┌──────────────────────────────────────────┐
│  server/       服务层（只转发）            │
│  路由 → engine → 序列化                    │
│  ★ 不放任何规则                            │
└──────────────────────────────────────────┘
              ↕ 函数调用
┌──────────────────────────────────────────┐
│  engine/       引擎（你）                  │
│  ★ 全部业务逻辑在这                        │
│  纯函数，可单独测试，不依赖 HTTP            │
└──────────────────────────────────────────┘
              ↕ 读
┌──────────────────────────────────────────┐
│  config/config.json   数据（第三位同学）   │
└──────────────────────────────────────────┘
```

### 3.2 为什么这样分

| 设计 | 好处 |
|---|---|
| **engine 不知道 HTTP 存在** | 可以直接写脚本测试，不用起服务器 |
| **server 不含规则** | 以后加联机只改这里，引擎不动 |
| **config 与代码分离** | 调数值不碰代码，第三位同学能独立工作 |
| **前端零计算** | 显示错了是前端问题，数字错了是引擎问题，**责任清晰** |

### 3.3 依赖方向（重要）

```
web ──→ server ──→ engine ──→ config
         ✗          ✗         ✗
      不许反向依赖
```

**engine 绝不 import server。** 这样引擎能脱离 Web 单独跑。

## 四、这个游戏实现的核心难点

### 4.1 真正的难点：**求值顺序**，不是算法

你的规则里有一条铁律：

> **本季产出的东西，不能用于本季已经开始的生产。**

这句话翻译成代码就是**顺序问题**：

```
❌ 错误：先把所有东西都算出来，再统一分配
✅ 正确：期初先扣掉本季要用的，季末才算本季产出
```

**类似陷阱还有**：

| 陷阱 | 正确做法 |
|---|---|
| 幸福度用哪一季的 H？ | **用上一季的**（否则循环依赖） |
| 粮食在哪扣？ | **结算时**（玩家要能选择买不买） |
| 市场价用哪一季的？ | 期初按**上期价**买，季末按**本期价**卖 |
| 效率影响劳动吗？ | **不影响**（`劳动 = d·u`，不乘 E） |

> **这些全是"顺序"和"谁乘谁"的问题，不是算法问题。**
> 所以真正的风险是**把顺序写错**，而不是写不出算法。

### 4.2 第二个难点：**共享资源的分配**

第一期只有你一个人，市场是"你 vs 系统"，**没有竞争**。

但结构上要留：

```python
def allocate_proportional(demand, supply):
    total = sum(demand.values())
    return {k: supply * v / total for k, v in demand.items()}
```

以后多人时，**换一个分配函数**即可（改成竞价、先到先得、按信用优先……）。

**这就是"单人跑、多人结构"的具体含义。**

### 4.3 第三个难点：**数值精度**

浮点数会有 `0.1 + 0.2 = 0.30000000000000004` 这种问题。

**M1 的验收数字是 `1049.65278`** —— 你要考虑：

| 做法 | 评价 |
|---|---|
| 全程 `float` | ✅ 简单，够用。比对时用 `abs(a-b) < 1e-6` |
| `decimal.Decimal` | 更准，但慢且麻烦 |
| **整数（分为单位）** | ✅✅ 最稳，但改造量大 |

**建议**：**用 `float`，测试时用容差比对**，别写 `assert cash == 1033.12`。

## 五、值得用的现成东西（就这几个）

### 5.1 后端

| 用途 | 推荐 | 为什么 |
|---|---|---|
| **HTTP 框架** | `FastAPI` | 自动生成 API 文档、自带数据校验；**或 `Flask`**（更小更简单） |
| **零依赖备选** | `http.server`（标准库） | 如果连装包都嫌麻烦，**标准库够用** |
| **数据校验** | `pydantic` | FastAPI 自带，能校验前端传来的 Plan |
| **测试** | `pytest` | 事实标准 |

> ⚠️ **`FastAPI` 还是 `Flask`**：你的接口只有 **2 个**（`GET /state`、`POST /advance`）。
> **两个都行，选你熟的。** 甚至标准库 `http.server` 都能跑。
> **别在这上面纠结** —— 这不是项目的难点。

### 5.2 前端

| 用途 | 推荐 | 说明 |
|---|---|---|
| **框架** | **不用**（原生 HTML/CSS/JS） | 12 个格子 + 几个面板，**上框架是负担** |
| 或者 | Vue / React | 如果前端同学**已经会**，那用也行 |
| **CSS 画格子** | `CSS Grid` | 原生，10 行搞定 |

> **前端同学零基础 → 强烈建议原生。** 学 React 的时间够他把界面写三遍。

### 5.3 明确不要用的

| ❌ 不要 | 原因 |
|---|---|
| 游戏引擎（Pygame/Arcade/Godot） | 解决的是渲染问题，你没有 |
| ECS 框架 | 为海量实体设计，你只有 12 个格子 |
| 数据库（PostgreSQL/MongoDB） | **存档就是一个 JSON 文件** |
| ORM（SQLAlchemy） | 没有数据库，不需要 |
| 消息队列 / Redis | 单人、无并发 |
| 状态管理库（Redux） | 前端只显示，无复杂状态 |
| 打包工具（Webpack/Vite） | 原生 JS 直接跑 |

## 六、如果一定要看看 GitHub

**看看可以，但目的是"抄思路"不是"抄代码"。** 值得看的类型：

| 看什么 | 学什么 |
|---|---|
| 类似的经营游戏（开源） | **数值怎么调的**、界面怎么布局 |
| 经济模拟 | **供需怎么建模** |
| 回合制游戏 | **回合推进怎么组织代码** |

**看的时候只问三个问题**：

1. 它的**状态对象**长什么样？
2. 它的**回合推进**怎么组织？
3. 它的**数值和代码**怎么分离？

**看完就关掉，自己写。** 因为：
- 你的规则是自己定的，**抄不了逻辑**
- 抄来的代码你不熟，**出 bug 时更慢**
- 黑客松时间紧，**读代码比自己写慢**

> **反直觉但真实**：这个项目的核心逻辑，**写得快的人 200 行就完了**。
> 花两天找一个"框架"，再用三天适配它，不如直接写两天。

## 八、回到你的问题

### Q：是否需要 GitHub 上找开源组件？

**A：不要找"游戏/模拟"类组件，可以用"通用基础设施"。**

| 类别 | 结论 |
|---|---|
| 游戏引擎 / ECS / 模拟框架 | ❌ **不要**，解决的不是你的问题 |
| 后端 Web 框架 | ✅ 可用（FastAPI/Flask/标准库都行） |
| 测试框架 | ✅ 可用（pytest） |
| 前端框架 | ⚠️ 零基础同学建议不用 |
| 数据库 | ❌ 存档就是个 JSON 文件 |

**一句话**：**轮子用现成的，规则自己写。**
你项目的价值在**规则**，不在**代码**——代码只是规则的翻译。

### Q：架构上要注意什么？

**三条**：

1. **分层清晰**：`web → server → engine → config`，**不许反向依赖**
2. **engine 是纯函数**：不依赖 HTTP、不依赖文件、可单独测试
3. **守五条红线**：`player_id` 索引、共享/私有分层、`advance(plans)`、可替换分配策略、服务层只转发

### Q：实现上最难的是什么？

**不是算法，是求值顺序。**

- 幸福度用**上一季**的 H
- 粮食在**结算时**扣
- 本季产出**不能**倒填本季已开始的生产
- 劳动**不乘**效率

这四条写错任何一条，数字就对不上，而且**很难查**。
所以：**测试先行**，用 M1 三个数当锚。
