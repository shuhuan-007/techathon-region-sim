## 一、先把循环说清楚

```
┌─────────────────────────────────────────┐
│  ① 行动阶段（唯一的"共同"阶段）           │
│     所有玩家同时做操作、提计划            │
│     ★ 只能提交一次，提交后锁定            │
└─────────────────────────────────────────┘
                  ↓
        所有人都点"结束季度"
                  ↓  ★ 屏障
┌─────────────────────────────────────────┐
│  ② 季度结算（服务端一次性算完）            │
└─────────────────────────────────────────┘
                  ↓
┌─────────────────────────────────────────┐
│  ③ 月报 / 结算报告                        │
└─────────────────────────────────────────┘
                  ↓
┌─────────────────────────────────────────┐
│  ④ 下一季的行动阶段                       │
└─────────────────────────────────────────┘
```

**关键：整局只有一个状态机循环，而且它极其简单。**

## 二、状态机（就三个状态）

```python
class Phase(str, Enum):
    COLLECTING = "collecting"    # 行动阶段：等玩家提交
    RESOLVING  = "resolving"     # 结算中（瞬时，实际不会停留）
    REPORT     = "report"        # 月报已出，等玩家看
```

**单人时它退化成什么？**

```
COLLECTING  →  玩家点"结束季度"  →  RESOLVING  →  REPORT  →  COLLECTING
                   ↑
              提交即全齐，屏障立即满足
```

**所以单人就是"点一下就结算"，没有任何等待逻辑。**

> **单人 ≈ 多人的特例。** `len(plans) == len(players)` 在单人时提交即成立。
> 这就是为什么"收齐 plans 再结算"这条红线是对的——**它是多人的默认行为，单人时自动退化成即时**。

---

## 三、"只能提交一次"带来的巨大简化

这条规则**消掉了一整类问题**：

| 原本要处理的 | 现在不需要了 | 为什么 |
|---|---|---|
| 请求队列 | ❌ | 没有并发请求 |
| 冲突合并 | ❌ | 没人能改 |
| 乐观锁 / 版本检查 | ❌ | 写入即锁定，不会覆盖 |
| "以最后一次为准"语义 | ❌ | 只有一次 |
| 重复提交幂等 | ❌ | 第二次直接拒绝 |

**`plans` 变成一个"只增不改"的字典**：

```python
plans[player_id] = plan     # 一次写入，永不修改
```

**幂等性还免费得到了**：重复提交同一个 player 直接拒绝，不会算两次。

## 四、修正后的服务端逻辑

```python
# server/app.py

class GameSession:
    def __init__(self, state, player_ids):
        self.state = state
        self.player_ids = player_ids
        self.plans: dict[str, Plan] = {}       # ← 只增不改
        self.phase = Phase.COLLECTING

    def submit(self, player_id: str, plan: Plan):
        """提交计划。只能提交一次。"""
        if self.phase != Phase.COLLECTING:
            raise Conflict("不在行动阶段")
        if player_id in self.plans:
            raise Conflict("已经提交过了，不能修改")   # ← 关键
        validate_plan(self.state, player_id, plan)
        self.plans[player_id] = plan

    def end_quarter(self, player_id: str):
        """玩家点'结束季度'。所有人到齐就结算。"""
        self.submit(player_id, self.plans.get(player_id) or Plan.end_turn(player_id))

        if len(self.plans) == len(self.player_ids):
            self._resolve()

    def _resolve(self):
        self.phase = Phase.RESOLVING
        engine.advance(self.state, self.plans)     # ★ 一次性算完
        self.plans.clear()                          # 清空，进入下一季
        self.phase = Phase.REPORT
```

**单人时**：`len(self.player_ids) == 1`，`end_quarter` 一调就进 `_resolve`。

> ⚠️ **注意**：`submit` 和 `end_quarter` 我分开了。你的描述里是"提交计划"然后"进入结算"，
> 如果**提交即结束**（没有单独的"结束季度"按钮），那 `end_quarter` 可以合并进 `submit`。
> **这一条要你确认**（见 §七）。

## 五、撤回我上一轮的过度设计

上一轮我按"通用多人游戏"给了几条建议。**在你这个"单一行动阶段 + 只能提交一次"的模型下，有三条是多余的：**

| 上轮建议 | 现在判断 | 原因 |
|---|---|---|
| **`revision` 版本号防并发覆盖** | ⚠️ **降级** | "只能提交一次+全齐才结算"下**并发覆盖不会发生**。<br>仍建议留字段，但**用途改为"存档版本 / 重放定位"**，不是并发控制 |
| **`command_log` 事件日志** | 🟡 **可选** | 仍有价值（调试/回放），但**不是多人必需**——因为结算是一次性的，全状态快照就够了 |
| **`Storage` 抽象成接口** | ✅ **仍建议** | 这条独立成立：换存储不动引擎，成本低 |

**我上轮说"多人存储的关键差异是要防并发覆盖"——在你这个模型下不成立。**
因为**根本不存在两个请求同时写同一局**：行动阶段是收集，结算是单点触发。

> **教训**：我按"通用多人游戏"（实时、可变、并发）给建议，
> 而你的游戏是"**回合制 + 一次性提交 + 屏障结算**"——**比通用模型简单得多**。
> 你的直觉是对的。

## 六、这套模型下真正需要注意的（只剩四条）

| # | 注意点 | 说明 |
|---|---|---|
| 1 | **`advance()` 必须是纯函数** | 结算是一次性的，**出错没有中间状态可回退**，只能靠重放 |
| 2 | **`plans` 是"只增不改"** | 别写成 `plans[pid] = plan` 允许覆盖 |
| 3 | **`_resolve` 用全量快照存档** | 结算完立刻存，因为这是唯一的持久化时机 |
| 4 | **提交要校验** | 服务端权威 —— 不信客户端传来的 Plan |

**第 1 条最关键**：因为结算"一次算完"，**如果算错，你不知道错在哪一步**。
所以：
- 不用 `random` / `datetime.now()`（保证可重放）
- **每一步算完可以记一条 debug log**（现金为何变了）

## 七、还需要你确认两点

| # | 问题 | 影响 |
|---|---|---|
| 1 | **"提交计划"和"结束季度"是同一个动作吗？** | 决定 `submit`/`end_quarter` 是否合并。单人时没区别，多人时有（可以先提交、再等别人） |
| 2 | **月报是"必须确认才能进入下一季"还是"自动进入"？** | 决定 `REPORT` 是阻塞态还是过渡态。单人时建议**看完点继续** |

**我的建议**：

- **提交 ≠ 结束季度**。保留两步更灵活，多人时玩家能"先看好再提交"
- **月报要确认**。因为这是玩家理解"我为什么亏了"的唯一时机
